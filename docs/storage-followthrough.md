# Storage follow-through

Updated 2026-10-19. This reconciles the remaining storage work with the current implementation. The original measurements in `storage-optimization-plan.md` describe the earlier GFL2 snapshot and are not current release bundle sizes.

## Implemented in this follow-through

- Removal now persists an inventory journal in `onlystory.media.v1` before clearing the installation. Undo retains the media for 30 seconds. Cleanup runs at startup and every 15 seconds, after the Undo window and any active import finish. It deletes only journaled `/private/` media that no retained installation or other Undo journal references. Reading saves and bookmarks remain intact. Covers, preview paths, shell files, unlisted cache entries, original-file caches and diagnostic workspaces are outside this cleanup's scope.
- Cleanup constructs a dry-run report containing candidate URLs and bytes before deletion. `reclaimRemovedMedia(readData)` exposes the same report without deleting by default. Destructive callers must pass `{ dryRun: false }`. It deletes the journal last, so a quota or process interruption can retry safely. A missing or invalid retained inventory blocks deletion instead of guessing about shared dependencies. PJSK's nested installation manifest expands into the full flattened dependency inventory, including model dependencies.
- Legacy cache migration hashes response streams incrementally with SHA-256 and reopens the cache-backed response for copying. It no longer skips files above 16 MiB or files without a Content-Length header. It also repairs an existing canonical entry from the verified old copy. Failed hashing/copying leaves the original key intact. Old paths continue to resolve through the alias index.
- Web Locks coordinate supported browser windows. Complete imports hold a shared library lock until installation reachability is persisted. Cleanup and migration take the exclusive lock. PJSK and ordinary media fetches take a per-identity lock and recheck the shared cache after acquiring it. BA imports take a common import lock so conversion/output reuse finishes before another window checks its requirements. Closing a window releases its browser locks. The per-window three-transfer bound remains in place.
- The existing toolbar selection now computes unique incremental pinned input bytes and bytes avoided through cached/shared inputs before the second press starts installation. PJSK uses the pinned source manifests, with repeated source URLs counted once across the selection. BA deduplicates original inputs by SHA-256 and verifies reusable outputs when determining which inputs remain necessary. BA says "Up to" because the native original-file cache can further reduce network reads. These are source-byte estimates, not a promise about the final converted disk footprint or browser quota. Unknown legacy files are explicitly unmeasured. Missing recipes report "Size unavailable" without preventing the established import workflow.
- Movie dependency selection accepts the common `MovieStreams` descriptor. In browsers that support both codec strings, an installation includes shared picture fragments plus the selected audio fragments. It excludes combined compatibility MP4s and other audio tracks. Without those codecs it selects the chosen combined MP4. Movie playback and exporter verification are handled in the accompanying movie-stream work, and this document does not substitute a storage helper test for playback evidence.

Undo expires when its media protection expires. If an expired or already-reclaimed journal cannot be found, Undo does not restore a false installation claim. Reinstalling a removed story starts a new dependency/language inventory instead of retaining old entries whose files may have been reclaimed.

## Verification

Focused unit verification passed 21 tests across `media-storage.test.ts`, `media-reclamation.test.ts`, `downloads/estimate.test.ts` and `downloads/pjsk.test.ts`. Cases include a 17 MiB stream with no Content-Length and a forbidden whole-file buffer method, revision-query cache identities, selected shared-movie fragments versus compatibility files, shared references, Undo after a new-language reinstall, nested inventories, safe blocking on missing inventories, interrupted cleanup retry and deduplicated estimates.

Chrome against the existing live Vite server passed all four `tests/storage-lifecycle.spec.ts` flows in one final run. Two windows request one shared asset only once. Cleanup waits for another window's library lock, then reads its newly persisted installation and preserves the shared payload. The real management UI removes an installed fixture, restores it with Undo, then removes it again and reclaims the unique media after expiry while retaining a second story's shared media. The expiry test advances the browser clock rather than waiting in real time. Toolbar selection measures a real pinned PJSK recipe without contacting its external source before the second press, and its estimate remains visible without header overflow at 320 pixels.

TypeScript checking passed after these changes. The parent task runs the combined final `npm run check` and release verification after all parallel implementation work settles. These focused checks do not establish Safari/Firefox compatibility, native source-cache reclamation or the entire movie playback acceptance list.

Six storage/server import checks passed. They verify shared fragment descriptors, complete immutable file inventories, nonoverlapping fragment timelines, duration coverage and retained compatibility paths. A development-host regression test also proves pinned gzip recipes reach `fetch` as compressed bytes. Vite previously advertised `.json.gz` as HTTP content encoding, causing browsers to decompress before SHA-256 checks. A narrow recipe middleware now preserves the compressed integrity contract for live development and the browser verification host.

`node scripts/verify-movie-streams.mjs` independently verified all 40 published descriptors, covering 23 unique picture/audio pairs in both languages. It concatenates initialization and fragments through file streams, then compares complete FFmpeg stream-copy H.264 Annex B SHA-256 hashes, unchanged AAC packet hashes and full packet counts with each original combined MP4. Every comparison passed. The machine-readable report is `movie-stream-verification.json`. This check caught a source movie whose picture ends after the older declared duration; the exporter now sets the common duration to cover every track endpoint. Exporter source-file hashing also uses a fixed 1 MiB buffer. Browser synchronization and interaction acceptance remain in the accompanying player verification.
